# G8 故障诊断 — 公开数据集选型调研

> 调研日期：2026-09-19
> 负责门类：**G8 故障诊断**（输入日志/异常堆栈/监控快照/告警 → 输出根因标签 + 可执行修复命令白名单）
> 主指标：根因命中率 Top-1 / Top-3（Top-3 ≥ 0.85）；辅助指标：修复命令可执行率、幻觉命令率 ≤ 1%

---

## 0. 结论先行（TL;DR）

1. **没有任何一个公开集能直接满足 G8 的金标形式**（「根因标签 + 可执行修复命令白名单」双字段）。现存公开集要么只有根因标签没有修复动作（RCAEval / Nezha / AIOps Challenge），要么只有自由文本答案没有可判分的命令白名单（OpsEval / OWL-Bench），要么只有代码补丁没有运维命令（SWE-bench / Defects4J）。
2. **最接近的两个是 AIOpsLab（微软）和 ITBench（IBM）**——它们是唯二同时覆盖「诊断 + 缓解动作」且带自动判分的 agent 评测环境，且仓库都活着（AIOpsLab 2026-09-19 刚推送、ITBench 2026-09-19 刚推送）。但它们是**交互式环境**不是静态题库，题量极小（AIOpsLab 48 problems、ITBench SRE 侧约 35 场景），且需要拉起真实 K8s 集群才能跑，无法直接当静态 benchmark 条目用。
3. **公开集对 G8 的可覆盖比例估计：15%–20%**。其中「可直接改造后入库」的约 5%（AIOpsLab/ITBench 的场景定义可转写成静态快照题），「只能作为素材/种子」的约 10%–15%（LogHub 原始日志、RCAEval/Nezha 的 trace+metric+log 三模态故障切片）。
4. **必须自建的部分**：① 修复命令白名单及其可执行性判分；② 幻觉命令检测；③ 中文运维语境（国内云厂商告警格式、中文工单、中文告警文案）；④ 覆盖到中间件/配置/依赖层的分层根因标签体系。这四项**公开集覆盖率接近 0**。
5. 一句话：**G8 走「小比例借用 + 大比例自建」路线**。不建议为了凑数把日志异常检测集（LogHub 系）算进契合列表——它们的任务形态是「日志模板解析 / 异常二分类」，与 G8 的「根因定位 + 修复动作」差两个层级。

## 2. 按任务形态分组小结

### 2.1 自然语言故障诊断问答 + 交互式修复（**唯一真正接近 G8 的一类**）
代表：**AIOpsLab、ITBench**（以及形态更浅的 OpsEval、OWL-Bench）。

- **离 G8 多远**：最近的一类，但仍有两道鸿沟。
  - **鸿沟一：交互式 ≠ 静态题**。AIOpsLab 和 ITBench 都要求 agent 在活的 K8s 集群里执行命令、观察、再决策，判分靠「系统是否恢复健康」。G8 的题面是「日志 + 堆栈 + 监控快照 + 告警」的**静态输入**，金标是**根因标签 + 命令白名单**。要用它们必须做「环境 → 快照」的转写。
  - **鸿沟二：题量**。AIOpsLab 48、ITBench SRE 侧约 35，加起来不到 100。G8 若要做到 Top-3 ≥ 0.85 的可信统计量，至少需要数百到上千条。
- **能借什么**：
  - **根因标签体系与故障类型分类法**（AIOpsLab 的 4 类任务划分、ITBench 的 94 个 incident pattern 是现成的分类学骨架，Apache-2.0 / MIT 可商用）。
  - **故障注入配方**：两者都用 Chaos Mesh 在 DeathStarBench / OpenTelemetry-demo 上注入，注入脚本可直接复用。
  - **评估范式**：「缓解后服务是否恢复」这个判分信号，比纯文本比对硬得多，值得吸收进 G8 的「修复命令可执行率」。
- **OpsEval / OWL-Bench 单独说**：这两个是**知识问答**不是**故障排查**——题面多为「以下哪项是 Nginx 502 的常见原因」这类，而不是给你一段真实日志让你定位。对 G8 主指标基本不可用。**唯一不可替代的价值是中文运维题面语料**，可作为自建题的措辞风格与术语表参考。

### 2.2 服务调用链根因定位（指标口径可借，输入形态不可借）
代表：**RCAEval、Nezha、Eadro、AIOps Challenge**。

- **离 G8 多远**：中等距离。**输出侧很近**（都是「定位到具体服务/组件 + Top-k 判分」，与 G8 主指标口径一致），**输入侧很远**（输入是 metric 时序、trace span、原始日志流，不是给人看的「监控快照 + 告警文本」），**修复侧完全缺失**（没有任何一个带修复动作）。
- **能借什么**：
  - **Top-k / Avg@k 判分实现**：RCAEval 的评测代码是 MIT、活跃维护，可以直接拿来当 G8 根因命中率的评分器基座。
  - **原始三模态故障切片**（见 §2.4，这是最大的价值）。
  - **故障类型枚举**：RCAEval 的 11 种故障类型 + Nezha 的资源类型/代码区域二维划分，可以并入 G8 的分层标签体系。
- **要警惕的**：AIOps Challenge 这类「多维指标下钻」任务，本质是统计定位问题，和 LLM 读日志推理根因是两码事，**不要因为它是中文的就抬高契合度**。

### 2.3 日志模板解析 / 日志异常二分类（**不是候选集，是原材料**）
代表：**LogHub、LogHub-2.0 / LogPub、Loghub-2k**。

- **离 G8 多远**：**最远**。这类任务的输出是「这条日志属于哪个模板」或「这段日志窗口是否异常（0/1）」。G8 要的是「为什么异常 + 怎么修」。中间隔着两个层级：异常检测 → 根因定位 → 修复决策。
- **明确结论**：**LogHub 系不应出现在 G8 的「可采用数据集」列表里**。把它们标为「适合 G8」是本次调研里最容易犯的错，也是上游明确提醒要避免的。
- **但它们的素材价值很高**：见 §2.4 与 §3.4。
- **许可证提醒**：GitHub API 显示 loghub / loghub-2.0 都是 **NOASSERTION（非标准开源许可证）**，搜索核实其条款为「学术研究免费、商用需邮件申请」。如果 G8 benchmark 有商用意图，**用 LogHub 日志文本做种子之前必须先走申请流程**，这是个实打实的法务动作，不能忽略。

### 2.4 【单独评估】原始日志 / trace 素材作为合成种子的价值

这是本次调研认为**公开集对 G8 唯一的高确定性贡献**，值得单列：

| 素材来源 | 提供什么 | 对 G8 的用法 | 许可证约束 |
|---|---|---|---|
| **LogHub / LogHub-2.0** | 19 个真实系统（HDFS、BGL、Thunderbird、Hadoop、OpenStack、Spark、OpenSSH…）的真实日志文本与模板 | 生成题面时，用真实模板渲染「噪声日志」，让故障信号埋在真实分布的日志流里，而不是 LLM 编的假日志。**这一点决定了 G8 题目的真实感上限** | **需申请商用许可** |
| **RCAEval RE2/RE3** | 270 + 90 个多模态（metric + log + trace）故障案例，每例都有确定根因 | 直接把一个案例的 telemetry 渲染成「监控快照 + 告警 + 日志片段」题面，根因标签复用其 ground truth。**这是最省力的一条造题捷径** | **MIT，可商用** ✅ |
| **Nezha** | 带代码区域级根因的多模态数据 | 造「深层根因」难题（同一现象、根因在应用代码 vs 在资源配额） | **MIT，可商用** ✅ |
| **Train-Ticket（41 微服务）+ Chaos Mesh** | 可自行拉起的真实微服务系统 + 工业级故障注入 CRD | 无限量自产新鲜故障案例，且**因为是新生成的，污染风险为零** | **Apache-2.0，可商用** ✅ |

**关键判断**：RCAEval（MIT）+ Train-Ticket（Apache-2.0）+ Chaos Mesh（Apache-2.0）这个组合，**许可证干净、仓库全部活跃、可商用**，构成了 G8 自建的最佳起点。相比之下 LogHub 虽然素材最好，但有商用许可障碍，建议只用于非商用版本，或先走申请。

### 2.5 代码 bug 定位修复（只借范式，不借数据）
代表：**SWE-bench、Defects4J、BugsInPy、DebugBench、GitBug-Java**。

- **离 G8 多远**：任务对象不同（源码 vs 运行时系统），但**评估哲学高度一致**：都是「给出一个可执行的修改 → 在真实环境里跑 → 看是否修好」。
- **能借什么（这部分很实在）**：
  - **SWE-bench 的「patch → 测试 → 通过率」** → G8 的「修复命令 → 沙箱执行 → 服务健康检查」。
  - **GitBug-Java 的「环境离线打包」** → G8 的修复命令必须在**固定版本的容器镜像**里执行，否则「命令可执行率」会随环境漂移。
  - **DebugBench 的「合成注入 bug」规模化方法** → 证明了合成故障可以做到 4,000+ 条且保持可判分，为 G8 大规模自建提供先例。
  - **SWE-bench 的污染教训** → 静态题库一旦公开就会腐烂。OpenAI 在 2026-02 停止报告 SWE-bench Verified 分数、改推 SWE-bench-Live 这类动态集，**这个教训应直接写进 G8 的设计：G8 必须保留一个不公开的 held-out 分片，并具备定期重新注入故障、刷新题库的能力**。
- **不借数据的理由**：这些是 Python/Java 源码修复题，与「运维故障诊断 + 运维命令」在能力维度上不重叠，硬塞进 G8 会污染门类定义。

### 2.6 安全事件响应与 ITSM 工单
- **安全（SOC 分诊）**：形态上确实是 G8 的邻域（告警 → 分诊 → 处置动作），但本次**没有核实到任何一个可确认下载、许可证明确的公开集**——SIABench / Legion / Simbian 都只在论文或厂商博客里出现。如实结论：**暂不可用，列为观察项**。
- **ITSM 工单**：**确认没有公开的真实企业工单集**。能找到的只有合成工单和匿名化的 helpdesk 分类数据，且任务是分类路由不是根因诊断。**对 G8 贡献为零。**

## 3. 自建路径建议

结论既然是「大比例自建」，下面给可落地的方案。

### 3.1 故障注入平台选型

**推荐组合：Train-Ticket + Chaos Mesh（主），OpenTelemetry-demo / Sock Shop / Online Boutique（副）**

| 选项 | 状态（实测 2026-09-19） | 建议 |
|---|---|---|
| **Chaos Mesh** | Apache-2.0，7,908 星，最近推送 **2026-09-10**，CNCF 孵化项目 | **首选注入引擎**。CRD 化（PodChaos / NetworkChaos / IOChaos / TimeChaos / StressChaos / DNSChaos / HTTPChaos / JVMChaos）意味着**故障定义本身就是结构化的 YAML，可以直接当根因 ground truth 使用**——这一点极其关键，它让「注入什么 = 标准答案是什么」自动对齐，省掉人工标注 |
| **Train-Ticket** | Apache-2.0，911 星，最近推送 **2025-11-21**，41 个微服务（Java/Node/Python/Go） | **首选被测系统**。多语言 + 41 服务，故障传播链足够长，能造出有区分度的题；且 RCAEval / Nezha / Eadro 都用它，**标签体系可与公开集对齐** |
| **Online Boutique / Sock Shop** | RCAEval 已在其上产出 735 案例 | 作为第二、第三套系统，保证题目不只来自单一架构 |
| **Chaos Monkey** | 面向 VM/实例级随机杀进程，粒度粗 | **不推荐**作为主力，故障类型太单一，难以支撑分层标签 |
| **DeathStarBench（AIOpsLab 用的）** | — | 若要与 AIOpsLab 结果可比，可加为第四套 |

**造题流水线**：
```
Chaos Mesh YAML（注入定义 = ground truth 根因）
  → 注入前后采集 Prometheus 指标 / Jaeger trace / 容器日志
  → 渲染成 G8 题面（告警文本 + 监控快照表格 + 日志片段 + 异常堆栈）
  → 人工/LLM 辅助编写修复命令白名单（多解）
  → 在同一镜像沙箱回放验证白名单命令确实能恢复服务
```
最后一步（回放验证）是保证「修复命令可执行率」这个指标有意义的前提，不能省。

### 3.2 根因标签体系设计（分层）

建议五层 + 双轴，既能对齐公开集，又能支撑 Top-1/Top-3 判分：

**L1 层级（5 层）**
1. **基础设施层**：节点宕机、CPU/内存/磁盘耗尽、磁盘 IO 饱和、网络分区、时钟漂移、DNS 故障
2. **中间件层**：数据库连接池耗尽、慢查询/锁等待、消息队列积压、缓存击穿/雪崩、代理（Nginx/Envoy）配置或上游超时
3. **应用层**：空指针/未捕获异常、内存泄漏、线程池耗尽、死锁、业务逻辑缺陷
4. **配置层**：环境变量缺失、资源 limit 设置过低、超时/重试参数不当、证书过期、feature flag 误开
5. **依赖层**：下游服务不可用、版本不兼容、第三方 API 限流/变更、级联失败

**双轴标注（每条题必须同时给）**
- **轴 A：故障定位** = `<服务/组件名>` + `<L1 层级>` + `<L2 具体故障类型>`
- **轴 B：故障机理** = 从「首个异常信号」到「用户可见症状」的传播路径（用于人工复核题目质量，不参与自动判分）

**Top-1 / Top-3 的判分口径必须提前钉死**：建议以「`<组件> + <L2 故障类型>` 二元组完全匹配」为命中。只匹配组件不匹配类型的算部分命中，单独统计——否则 Top-3 ≥ 0.85 这个目标很容易被「猜中服务名」刷上去。

**与公开集的对齐**：L1/L2 的枚举建议直接吸收 Chaos Mesh 的 CRD 类型（注入什么就是什么层）+ RCAEval 的 11 种故障类型 + ITBench 的 incident pattern 清单，这样将来若要引用公开集结果，标签是可映射的。

### 3.3 修复命令白名单维护 + 幻觉命令率自动检测

**白名单数据结构**（每道题一份）：
```yaml
root_cause: {component: ts-order-service, layer: middleware, type: db_conn_pool_exhausted}
fix_whitelist:
  - id: fix-1
    commands:
      - "kubectl -n ts scale deploy ts-order-service --replicas=4"
    verify: "curl -sf http://ts-gateway/health | jq -e '.status==\"UP\"'"
  - id: fix-2
    commands:
      - "kubectl -n ts set env deploy ts-order-service DB_POOL_MAX=50"
      - "kubectl -n ts rollout restart deploy ts-order-service"
    verify: "..."
forbidden_patterns:          # 明确的负向样本
  - "kubectl delete ns ts"
  - "rm -rf"
allowed_binaries: [kubectl, helm, curl, jq, systemctl, docker, psql, redis-cli]
```
**要点**：白名单必须**多解**（同一根因常有扩容/改配置/重启多条合法路径），否则可执行率指标会严重低估模型。

**幻觉命令率的四级自动检测**（建议逐级过，任一级失败即判为幻觉）：

| 级别 | 检查 | 实现方式 |
|---|---|---|
| **L1 二进制存在性** | 命令的可执行文件在评测镜像里存不存在 | 在固定镜像内 `command -v <bin>`；不存在 → 幻觉。这一级能抓掉绝大多数编造的工具名 |
| **L2 子命令 / 参数合法性** | `kubectl scale --replica=4`（少个 s）这类编造的 flag | 对高频工具（kubectl / helm / docker / systemctl）预生成**参数字典**（从 `--help` 或 `kubectl api-resources` 自动抽取），逐 token 校验；未知 flag → 幻觉 |
| **L3 资源存在性** | 命令引用了集群里不存在的 namespace / deployment / service | 对照评测时刻的集群资源快照做实体校验；引用不存在的对象 → 幻觉。**这一级最能抓住「模型编了一个服务名」这种典型错误** |
| **L4 语义/安全边界** | 命令语法可解析、不在 `forbidden_patterns` 里、不越出 `allowed_binaries` | 用 `bashlex` / `shellcheck` 做语法解析 + 正则黑名单 + 白名单二进制集合校验 |

**幻觉命令率 = （L1∪L2∪L3 命中的命令数）/（模型产出的命令总数）**。注意 L4 抓到的是「危险命令」不是「幻觉命令」，建议**单列一个「危险命令率」指标**，不要和幻觉率混在一起——它们要传达的问题不同。

要压到 **≤ 1%**，L1–L3 必须全自动、无人工介入，且评测镜像版本必须固化（参考 GitBug-Java 的离线环境打包做法）。

### 3.4 LogHub 素材作为合成种子的具体用法

1. **先解决许可证**：loghub 的 GitHub 许可证字段实测为 NOASSERTION，条款为学术免费 / 商用需向 `info@logpai.com` 申请。**商用前必须走这一步**，否则整个 G8 题库带法务瑕疵。若不想走流程，直接用 RCAEval（MIT）+ 自采 Train-Ticket 日志替代。
2. **用法一：噪声背景**。从 LogHub 对应系统（HDFS / OpenStack / Hadoop / Spark）抽取正常时段日志作为背景流，把自己注入的故障信号插进去。控制**信噪比**（故障相关日志占比 0.1% / 1% / 5% 三档）来生成难度梯度——这是低成本做难度分层的好办法。
3. **用法二：模板库**。用 Loghub-2k 的人工标注模板（每系统 2,000 行）作为**日志措辞词典**，让合成日志的格式、字段、缩写符合真实系统习惯，避免 LLM 生成的日志「一看就是假的」。
4. **用法三：长上下文压力测试**。LogHub-2.0 每系统 360 万+ 条，可截取 10k / 50k / 200k token 的日志窗口，测 G8 在长上下文中定位根因的能力衰减曲线。
5. **不要做的事**：不要把 LogHub 自带的「异常 0/1 标签」当成 G8 的根因标签。HDFS/BGL 的异常标签只说「这个 block/这条日志异常」，不说根因是什么，直接用会产出错误金标。

### 3.5 建议的自建规模与节奏

| 阶段 | 产出 | 来源配比 |
|---|---|---|
| **P0（种子，约 100 条）** | 手工精标，覆盖 5 个 L1 层级各 20 条 | 全部来自 Train-Ticket + Chaos Mesh 自注入，人工写白名单，验证流水线跑通 |
| **P1（约 400 条）** | 半自动扩充 | 60% 自注入、30% 从 RCAEval RE2/RE3 案例转写、10% 中文语境改写 |
| **P2（约 1,000+ 条）** | 规模化 | 自动注入 + LLM 辅助生成白名单 + 沙箱回放验证过滤；保留 20% 作为**永不公开的 held-out 分片** |

## 4. 「覆盖不到什么」的诚实说明

### 4.1 可覆盖比例估计：**15%–20%**

拆解依据（按 G8 一道完整题目所需的四个要素加权）：

| G8 要素 | 权重 | 公开集覆盖情况 | 覆盖率 |
|---|---|---|---|
| **① 故障输入素材**（日志 / trace / 监控快照 / 告警） | 30% | LogHub、RCAEval、Nezha 提供大量真实素材，但需转写成快照形态；许可证有一处（LogHub）需申请 | **~50%** |
| **② 根因标签** | 30% | RCAEval / Nezha 有服务级+类型级标签，可映射；但缺中间件、配置、依赖层的细分，且无中文 | **~30%** |
| **③ 可执行修复命令白名单** | 30% | **公开集中完全不存在**。AIOpsLab / ITBench 有「缓解动作」但判分是「服务是否恢复」，不提供命令白名单本身 | **~0%** |
| **④ 判分器 / 评估范式** | 10% | RCAEval 的 Top-k 评分器、SWE-bench 的可执行判分范式、AIOpsLab/ITBench 的环境判分，都可直接借用 | **~60%** |

加权：0.3×50% + 0.3×30% + 0.3×0% + 0.1×60% = **30% 的「要素级」覆盖**。但「要素齐了」不等于「题能用」——考虑到还要做形态转写、中文化、白名单编写与回放验证，**折算成「可直接入库的成品题目比例」应下调到 15%–20%**。

### 4.2 明确覆盖不到的五件事

1. **修复命令白名单——覆盖率 0%。** 这是 G8 金标的一半，没有任何公开集提供。100% 自建，且是工作量最大的一块。
2. **幻觉命令率检测——覆盖率 0%。** 没有现成的运维命令幻觉检测基准。AgentHallu / MIRAGE-Bench 是通用 agent 幻觉评测，不含运维命令的二进制/参数/资源三级校验。工具链要从零搭。
3. **中文运维语境——覆盖率接近 0%。** OpsEval / OWL-Bench 有中文题面但是知识问答；AIOps Challenge 是中文但形态是指标下钻且许可证 NC + 外链腐烂。**国内云厂商（阿里云/腾讯云/华为云）的告警格式、中文日志、中文工单，公开集里一条都没有。**
4. **企业 IT 支持 / 真实工单——确认无公开集。** 不是「没找到」，是结构性不存在（PII + 客户合同限制）。
5. **配置层与依赖层根因——覆盖极薄。** 公开集的故障注入以基础设施层为主（CPU/内存/网络/延迟），对「证书过期」「超时参数配错」「下游版本不兼容」这类真实生产中最高频的配置/依赖类故障，几乎没有样本。这一层必须自己注入。

### 4.3 两个额外风险提示

- **污染风险不对称**：静态文本类（OpsEval、OWL-Bench、SWE-bench、Defects4J、LogHub）污染都很高；telemetry 数值类（RCAEval、Nezha）污染低。这进一步支持「用 telemetry 造题、不用现成文本题」的路线。
- **静态题库会腐烂**：SWE-bench 的前车之鉴（2026-02 起 OpenAI 停止报告其 Verified 分数）说明，G8 从第一天就应该设计成**可周期性重新注入、刷新题面**的动态 benchmark，而不是发布一次就固定的静态集。
