## 3. 沙箱与环境选型要点

1. **SQL 沙箱三层底座**：L1（默认）SQLite 承载 BIRD / Spider 1.0 / KaggleDBQA / 自建中文库；L2（可选）PostgreSQL in Docker 承载 BIRD-CRITIC 的 PG 分支与需要窗口函数/CTE 的自建题；L3（专项）DuckDB 承载 Spider2-lite 本地可执行部分与 Parquet/CSV 直查。**不上 BigQuery/Snowflake**——需外部云账号，既有成本又有配额风险。
2. **为什么选 BIRD 的 SQLite 而非 SWE-bench 的 Docker 作底座**：BIRD 全是 SQLite 单文件库，重置 = 复制一个文件（毫秒级），33.4 GB 是全量上限、Mini-Dev 只要几百 MB；SWE-bench 方案 ≥120 GB 起、全缓存 240–684 GB，重置是重建容器（秒级到分钟级），对 SQL 这种高频短查询完全不划算。
3. **SQL 状态重置**：母本 `chmod 444` 放共享只读目录，每 task 起一个 tmpfs 目录用 `cp --reflink=auto` 复制、结束整目录 `rm -rf`，绝不允许任务间共享同一 db 文件句柄；PG 用 template database（`CREATE DATABASE task_x TEMPLATE bird_critic_base`，跑完 DROP），比重启容器快一到两个数量级，容器每 200 个任务回收一次防连接泄漏；每 task 前强制校验母本 checksum。
4. **SQL 限额与隔离**：单条 SQL 硬超时 30 s（SQLite 用 `progress_handler` 中断，PG 用 `statement_timeout = 30000`），单 task 总超时 120 s，容器 `--memory=2g --memory-swap=2g`；默认只读连接，仅 DDL/DML 类任务（BIRD-CRITIC 里有）才在 CoW 副本上开写；SQLite 关掉 `load_extension`，PG 用受限角色禁 `COPY ... TO PROGRAM` / `pg_read_file` / 大对象 / `dblink`；默认 `--network=none`。
5. **Python 沙箱两个镜像**：`sandbox-py-analysis`（pandas / numpy / scipy / matplotlib / openpyxl / pyarrow / duckdb，服务 G6 的 DABStep、InfiAgent、DSBench、DS-1000）与 `sandbox-py-code`（BigCodeBench 全部 139 个库、77 标准 + 62 第三方，版本锁死，`pip freeze` 产物入版本控制，服务 G7-Code）。两个镜像都 pull 到私有 registry 并按 digest 引用，不用 tag。
6. **Python 运行时**：每 task 起全新容器（不复用容器 + 清目录——后者清不掉内存态、环境变量、后台进程、pip 副作用），根文件系统 `--read-only` + 只挂一个 tmpfs `/workspace`（1–2 GB），数据文件 `:ro` 挂载；单次执行 60 s（分析类可放宽到 180 s）、单 task 墙钟 300 s、`--memory=4g --cpus=2 --pids-limit=256`、`ulimit -f` 限 1 GB、`--network=none`、`--security-opt no-new-privileges`、`--cap-drop=ALL`、非 root；常驻 N 个 paused 容器作预热池（BigCodeBench 导入 139 个库的冷启动不可忽略）。
7. **结果集等价判定——结构维度**：实现 `result_equiv(pred_rows, gold_rows, mode)`，默认 `mode="bag"`。**行序**默认忽略（每行 tuple 规范化后排序再比），除非金标 SQL 出现 `ORDER BY` 且该 ORDER BY 配合 `LIMIT`/`TOP` 影响输出语义，此时严格比行序；**列序**默认忽略（按列值多重集做二分图匹配），同时保留严格模式作对照、报两个数；**列名/别名**忽略；**列数**严格相等，多带一列判错但单独统计为 `extra_column` 错误类。
8. **结果集等价判定——数值与 NULL**：浮点用 `abs(a-b) <= max(atol, rtol*abs(b))`（`atol=rtol=1e-6`，金额类单独一档 `atol=0.01`，比较前统一 round 到金标有效位数）；`5` 与 `5.0` 判等；金额走 `decimal.Decimal` 解析不走 float；**`NULL == NULL` 在结果集比较中判等**（与 SQL 三值逻辑相反——这是结果集比较不是 SQL 求值），`NULL` 与 `0`、`''`、`'NULL'` 字符串判不等（最常见的隐蔽 bug 就是把 NULL 当空串）。
9. **结果集等价判定——字符串与时间**：默认 `strip()` 两端空白、大小写敏感（除非金标全大写/全小写且任务无关大小写）、Unicode 做 **NFKC 归一化**（中文全角/半角是真实坑）；日期统一 parse 成 UTC datetime 后比，`'2024-01-01'` 与 `'2024-01-01 00:00:00'` 判等；布尔 `True/1/'t'/'true'` 视为等价；空结果集双方都空判对但单独统计比例（某题 >30% 模型都返回空集则标记该题可疑）；超 10 万行只比规范化排序后的 SHA256 checksum。**上面每一条都要写成独立单元测试**——checker 自身的 bug 会系统性污染所有指标且极难事后发现。
10. **G8 故障注入平台选型**：**Chaos Mesh**（Apache-2.0，CNCF 孵化，7,908 星，最近推送 2026-09-10）作首选注入引擎——它的 CRD（PodChaos / NetworkChaos / IOChaos / TimeChaos / StressChaos / DNSChaos / HTTPChaos / JVMChaos）本身就是结构化 YAML，**「注入什么 = 标准答案是什么」自动对齐，省掉人工标注**；**Train-Ticket**（Apache-2.0，41 个微服务，911 星，最近推送 2025-11-21）作首选被测系统（故障传播链足够长，且 RCAEval / Nezha / Eadro 都用它，标签体系可与公开集对齐），Online Boutique / Sock Shop 作第二三套。造题流水线：Chaos Mesh YAML（= ground truth 根因）→ 注入前后采集 Prometheus 指标 / Jaeger trace / 容器日志 → 渲染成 G8 题面（告警文本 + 监控快照表格 + 日志片段 + 异常堆栈）→ 人工/LLM 辅助编写修复命令白名单（多解）→ **在同一镜像沙箱回放验证白名单命令确实能恢复服务**。最后一步不能省，它是「修复命令可执行率」这个指标有意义的前提。

## 5. 本片污染要点

1. **HumanEval 已被证实污染，不是「可能被污染」**：每条 prompt 在 GitHub 上中位数 **99 次**命中；The Pile 中 **12.2%**、The Stack 中 **18.9%** 样本重合；RedPajama-1T / StarCoder-Data 与其重合 **8–18%**。更隐蔽的是间接泄漏：Evol-Instruct 等由 GPT-3.5/4 生成的合成微调集里重现了语义等价的 HumanEval 题目——在受污染合成集上训练可让 HumanEval pass@1 虚高**最多 14 个绝对点**，而在未污染的 LBPP 上几乎不变；顶尖模型换到新鲜集上掉幅可达 **43%**。
2. **MBPP 同源同理且题目更简单、饱和更早**；**Spider 1.0 已饱和**——o1-preview 类 agent 达 **91.2% EX**、GPT-4o 达 **86.6%**，schema 小而干净、标注 SQL 全网可见；CSpider 是其中文翻译，继承全部污染。结论：我方 G7 门槛是 pass@1 ≥ 0.8，用一个已被背过的集设门槛等于门槛不存在。
3. **SWE-bench Verified 的隐性污染（本片最大风险）**：500 条中 **97.8%** 的评测用测试文件在 `base_commit` 时点前已公开；**92.8%** 的修复 commit 可用 issue 号直接在公开 GitHub 历史搜到；**60.83%** 的已解决 issue 存在「解法泄漏」（issue 正文/评论里写明了做法）。过滤泄漏题与弱测试后（SWE-bench+），平均解决率从 **51.7% 掉到 25.9%**。**人工校验过 ≠ 干净**——泄漏问题并未因人工校验而消除。佐证：OpenAI 已于 2026-02 停止报告标准 SWE-bench Verified 分数，改推 SWE-bench-Live / SWE-Rebench / SWE-MERA。因此该集只能作专项探针，且报告时必须同时给出「泄漏过滤后」的分数。
4. **EvalPlus 不解决污染**：HumanEval+ / MBPP+ 的强化测试解决的是「假阳性」，题面完全不变，记忆化路径完整保留——测试变严 ≠ 抗污染。
5. **有抗污染机制的集之一：LiveCodeBench 时间切片**。每题带精确平台发布日期，评测时只取模型训练截止日之后发布的题；已实证有效——DeepSeek-Instruct-33B 在其 2023-09 发布日之后的 LeetCode 题上性能显著下滑，GPT-4o 在 2023-11 训练截止之后的题上同样下滑。落地做法：给所有题加 `publish_date` 字段，双轨报告 `score_all`（对齐外部 leaderboard）与 `score_fresh`（只算 publish_date > 训练截止日），**`score_fresh` 是准入的唯一依据**；模型未公开训练截止日则按「发布日 − 6 个月」保守估计并在报告中注明。
6. **有抗污染机制的集之二：BIRD-CRITIC 的 200 条 held-out OOD**，是明确的抗污染设计，报告建议整体放进 test；SQL 侧另每季度从真实报障场景新造 30–50 条滚动补充。
7. **饱和度熔断规则**：任一集上排名前 3 的模型平均分 **> 85%** 时自动标记「该集已饱和」，下一季度降级为 dev；做成自动检查不靠人记。另建议对关键题维持「原版 / 变异版」双版本，长期跟踪两者分差——分差扩大是污染加剧的早期信号。
8. **G8 的污染风险不对称**：静态文本类（OpsEval、OWL-Bench、SWE-bench、Defects4J、LogHub）污染都很高——LogHub 是被引用最多的日志集几乎必然在训练语料中，Defects4J 存在 12 年、全网教材级；而 telemetry 数值类（RCAEval、Nezha）污染低，因为它不以文本形式存在于训练语料。这进一步支持「用 telemetry 造题、不用现成文本题」的路线；自注入的 Train-Ticket + Chaos Mesh 案例污染风险为零。
